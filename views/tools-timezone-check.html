What this test actually measures

There are two completely separate places a website can learn "what time it is where you are", and they almost never come from the same source.

The first is your browser timezone. Any page can call a JavaScript API and get back an IANA zone name such as Europe/London or Asia/Kolkata, plus the current offset from UTC in minutes. That value comes from your operating system's date and time settings. Nothing on the network touches it. If you set your laptop clock to Tokyo, every website you visit believes you are in Tokyo.

The second is your IP timezone. When a request reaches this server, the server looks the source IP up in a geolocation database and reads off the timezone recorded for that block of addresses. That value comes from whoever registered and routes the address range — your ISP, your mobile carrier, or the hosting company running the VPN server you are connected to.

The test above puts the two side by side and subtracts one offset from the other. If the difference is zero, the two stories agree. If it is not zero, they disagree, and the size of the gap is often a strong hint about what is going on.

Why a timezone mismatch gets you flagged

A VPN or proxy changes exactly one thing: the IP address the server sees. It does not, and generally cannot, change your operating system clock. That asymmetry is what makes this check so widely used.

Consider someone in India who connects to a VPN endpoint in Frankfurt. Their IP now geolocates to Germany, so the server-side timezone reads Europe/Berlin. Their laptop clock is still set to Indian Standard Time, so the browser reports Asia/Kolkata. The offsets differ by roughly three and a half hours. No sophisticated fingerprinting is needed to notice that — a few lines of JavaScript and one database lookup are enough.

Because the check is cheap to run and cheap to reason about, it turns up in a lot of places: streaming platforms enforcing regional licensing, banks and payment processors scoring a transaction for fraud risk, ticketing and sneaker sites blocking resellers, online exams verifying that a candidate is where they claim to be, and account-security systems deciding whether a login looks unusual. In most of these systems a mismatch is not an automatic block. It is a weighted signal that gets added to others, such as whether the IP belongs to a hosting provider rather than a residential ISP.

A half-hour or forty-five-minute offset is particularly revealing, because relatively few zones use them. India, Iran, parts of Australia, Nepal and Newfoundland are among the exceptions. A browser reporting a +05:30 offset from an IP that geolocates to a whole-hour European zone narrows the possibilities considerably.

Innocent reasons the two disagree

A mismatch is not proof of anything. Plenty of ordinary situations produce one, and it is worth being clear about them before treating the result as evidence.

  • You are travelling. Laptops do not always pick up the local timezone, especially if automatic time setting is switched off or the machine has been asleep. Someone flying from London to Singapore may keep a British clock for days.
  • Your system clock is simply wrong. Timezone is set manually more often than people realise, and a machine restored from a backup or reimaged in another office can carry the old setting for a long time.
  • Mobile networks route oddly. Carriers frequently hand out addresses from a pool registered to a gateway in a different city or even a different country from where the handset actually is. Roaming makes this worse.
  • Corporate networks backhaul traffic. A company may route all internet traffic through a single egress point at head office. Staff in a branch office appear to be wherever that egress lives.
  • The browser is running in a datacentre. Remote desktops, cloud browsers, CI runners and headless automation all have IPs registered to hosting providers, and their container clocks are very often left on UTC.
  • The geolocation database is stale or coarse. Address blocks get reassigned between regions, and some records only ever resolve to a country centroid. The timezone attached to an IP is an estimate, not a measurement.
  • Privacy tooling is deliberately lying. Some hardened browsers and extensions report UTC as the browser timezone on purpose, to reduce fingerprinting. That produces a mismatch for nearly everyone who uses them.

How to fix a mismatch

If you want the two values to agree, the fix is almost always on the operating system side rather than the browser side.

  1. Decide which story you want to tell. If your goal is for both values to reflect where you physically are, turn the VPN off and set the system clock to your real local zone. If your goal is for both to match the VPN exit, change the system timezone to the exit's zone.
  2. Set the system timezone manually. On Windows this is Settings, Time & language, Date & time. On macOS it is System Settings, General, Date & Time. On Linux, timedatectl set-timezone Europe/Berlin. Automatic timezone detection often relies on Wi-Fi and location services, which a VPN does not influence, so manual is more predictable.
  3. Restart the browser. Some browsers cache the resolved timezone for the lifetime of the process and will keep reporting the old zone until relaunched.
  4. Check whether an extension is overriding it. Anti-fingerprinting and timezone-spoofing extensions take precedence over the system setting and are a common cause of a mismatch that survives every other fix.
  5. Re-run this test. Reload the page and confirm the verdict tile reads MATCH.

Bear in mind that matching the two values only removes one signal. If the IP still belongs to a well-known hosting range, that is visible independently — the VPN and proxy check looks at exactly those characteristics, and reverse DNS often names the hosting provider outright.

Limitations of this check

The browser side of this test is reliable in the sense that it accurately reports what your browser claims. It says nothing about whether that claim is true. The IP side is the weaker half: timezone is derived from a geolocation record, and IP geolocation is approximate. City-level results can be tens of kilometres out, and country-level errors happen with reassigned blocks, satellite links, and carrier-grade NAT.

Two zones can also share an offset while being different places. Europe/London and Africa/Abidjan are both UTC+0 in winter but not in summer, so the same pair of zones can match in January and mismatch in July. The tool reports both the zone names and the numeric offsets so you can see which kind of agreement you have.

Finally, this page tests one address at a time against your own browser. If you need to profile many addresses, the bulk lookup tool returns timezone and offset for a list of IPs, and the same fields are available programmatically — see the API documentation for /api/me and /api/lookup/:ip.

Common questions

What is timezone dissonance?

It is the condition where the timezone reported by a visitor's browser does not match the timezone associated with their IP address. The term is mostly used in fraud detection and bot-mitigation work, where the gap between the two values is treated as a risk signal rather than a fact about location.

Does a mismatch prove I am using a VPN?

No. It is consistent with VPN use, but travelling with a laptop still set to your home timezone produces the same result, as does a manually misconfigured clock or a mobile IP registered in another city. Treat it as one input among several. The VPN and proxy check looks at independent evidence such as whether the address sits in a hosting range.

Can I hide the mismatch by changing my browser timezone?

Changing the operating system timezone to match your VPN exit will make this particular test read MATCH. It does not hide anything else: the address itself, its reverse DNS, and the network it belongs to are all still visible, and a browser that reports a zone inconsistent with its own locale and language settings can look odder than the original mismatch.

Why does my IP timezone look wrong even without a VPN?

Because it comes from a database record about your ISP's address block, not from your device. Mobile carriers and large ISPs often route traffic through a hub in another city, and reassigned address ranges can carry outdated entries for months. See the general FAQ for more on geolocation accuracy.

Is my timezone stored when I run this test?

No. The browser timezone is read in your browser and compared in your browser. The server only performs the geolocation lookup for the address you tested, exactly as the homepage lookup does, and it does not receive your browser timezone value.
